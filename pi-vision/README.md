# pi-vision — ตรวจจับใบหน้าและวัดสมาธิ

โค้ดฝั่ง Raspberry Pi 5 สำหรับ Focus feature ของ ENV//MONITOR
ใช้ **MediaPipe Face Landmarker** (Tasks API รุ่นใหม่ ไม่ใช่ `solutions.face_mesh` ที่เลิกใช้แล้ว)

> **สถานะ: โหมดดูผลบนหน้าจอเท่านั้น** — ยังไม่ส่งข้อมูลออกนอกเครื่อง
> ตั้งใจให้รันดูค่าและปรับ threshold ให้เข้ากับตัวเองก่อน แล้วค่อยต่อกับ Supabase
> ดู [§ ต่อกับแดชบอร์ด](#ต่อกับแดชบอร์ด) เมื่อพร้อม

## สามโหมด — เลือกตอนเปิดโปรแกรม

รันเฉย ๆ แล้วโปรแกรมจะถามก่อนเริ่ม

```
$ python3 main.py

  เลือกโหมดการทำงาน
    1) ห้องรวม    (ค่าเริ่มต้น)
       นับคน + การหันหน้ารวมของห้อง ไม่แยกรายบุคคล ไม่วัดตา ไม่เก็บลายเซ็นใบหน้า
    2) รายบุคคล
       ติดตามแยกทีละคนด้วย id · วัดการกะพริบตาและความง่วง · จำ id ได้เมื่อกลับมา
    3) เฉพาะคนในรูป
       รู้จักแค่คนที่มีรูปใน faces/ · ไม่เก็บลายเซ็นของคนอื่นไว้จำ · คนที่ไม่มีรูปไม่ถูกบันทึก

  เลือก [1]:
```

ข้ามคำถามได้ด้วย `--mode room` / `--mode person` / `--mode known`
หรือตั้ง `VISION_MODE` ไว้ใน `.env`
ลำดับความสำคัญคือ **flag > .env > ถาม** และถ้ารันในที่ที่ไม่มีหน้าจอถาม
(cron · systemd · ท่อ) จะไม่ค้างรอ input แต่ใช้โหมดห้องรวมแล้วแจ้งให้รู้

### เลือกกล้องก่อนเริ่ม

ถัดจากคำถามเรื่องโหมด โปรแกรมจะสำรวจกล้องที่เสียบอยู่แล้วให้เลือก

```
[pi-vision] กำลังสำรวจกล้อง…

  เลือกกล้อง
    1) CSI camera (Picamera2)
    2) Integrated Camera
    3) c922 Pro Stream Webcam

  เลือก [1]:
```

การสำรวจ**ไม่เปิดกล้องสักตัว** — ถาม v4l2 บน Linux และถาม DirectShow บน Windows
เอาแค่รายชื่อ ใช้เวลาราว 0.15 วินาที ตอนแรกเคยทำด้วยการไล่เปิด `cv2.VideoCapture`
ทีละ index ซึ่งบนเครื่อง Windows เครื่องหนึ่งใช้เวลา **64 วินาที** เพราะกล้องในตัว
เครื่องตัวเดียวกินไป 63 วินาทีตอนเปิด · ผลพลอยได้คือได้**ชื่อรุ่น**มาโชว์ในเมนูด้วย

ถามเฉพาะเมื่อมีเหตุให้ถามจริง — **เจอกล้องตัวเดียวก็ไม่ถาม** (คำถามที่มีคำตอบเดียว
ไม่ใช่ตัวเลือก มันแค่ทำให้เริ่มช้าลง) และ**ไม่เจอกล้องเลยก็ไม่ถาม** ปล่อยให้
`Camera.open()` รายงานปัญหาจริงซึ่งบอกสาเหตุได้ดีกว่ารายการว่าง ๆ

ถามก่อนดาวน์โหลดโมเดลและก่อนเปิดกล้อง เพื่อไม่ให้ผู้ใช้รอเสร็จแล้วค่อยมาเจอคำถาม

| ไม่อยากให้ถาม | ทำอย่างไร |
|---|---|
| ครั้งเดียว | `--source usb` (ระบุมาแล้ว = ไม่ต้องถาม) |
| ถาวร | `CAMERA_ASK=false` ใน `.env` แล้วตั้ง `CAMERA_SOURCE`/`CAMERA_USB_INDEX` เอง |
| ปักกล้องตัวที่ต้องการ | `CAMERA_USB_NAME=c922` — ตั้งแล้วไม่ถามเลย ไม่ต้องตั้ง `CAMERA_ASK` ด้วย |
| รันผ่าน systemd/cron | ไม่ต้องทำอะไร — ไม่มี TTY ก็ไม่ถามและไม่ค้างรอ input |

สลับกล้องระหว่างรันได้เหมือนเดิมด้วยปุ่ม `v` และเปลี่ยนความละเอียดด้วยปุ่ม `r`

#### ปุ่ม `r` — เปลี่ยนความละเอียดขณะรัน

```
  choose resolution
    1. 1280x720   1.78   up to 10fps
    2. 960x720    1.33   up to 15fps
    3. 1024x576   1.78   up to 15fps
    4. 800x600    1.33   up to 24fps
    5. 864x480    1.80   up to 24fps   (current)
    6. 800x448    1.79   up to 30fps
    7. 640x480    1.33   up to 30fps
    8. 640x360    1.78   up to 30fps
    9. 432x240    1.80   up to 30fps

  press 1-9 to switch  ·  r / Esc to close
```

รายการมาจากที่ไดรเวอร์บอกว่ากล้องรองรับจริง ไม่ใช่รายการที่เขียนตายไว้ —
เสียบกล้องคนละรุ่นก็ได้รายการของรุ่นนั้น · ตัวเลข fps คือของโหมด**ไม่บีบอัด**
ซึ่งเป็นค่าที่ตรงกับของจริงที่ได้ (ดูหัวข้อขนาดภาพด้านล่าง)

- โหมดที่ช้ากว่า 10fps ไม่ถูกแสดง — กล้องมักมีโหมดความละเอียดสูงที่วิ่งได้ 2fps
  ซึ่งใช้กับงานนี้ไม่ได้ และถ้าปล่อยไว้จะกินช่องเลข 1–9 จนโหมดที่ใช้ได้จริงหลุดรายการ
  (C922 มีโหมดแบบนั้นสี่ตัวเรียงอยู่หัวลิสต์พอดี)
- การเปลี่ยนโหมดต้องปิดแล้วเปิดกล้องใหม่ ใช้เวลาราว **2.3 วินาที** ภาพจะค้างช่วงนั้น
- เลือกเองแล้วระบบจะ**เลิกเลือกขนาดให้อัตโนมัติ** จนกว่าจะรีสตาร์ต ไม่งั้นมันจะดึงกลับ
  ไปโหมดที่มันคิดว่าดีที่สุดทันที แล้วปุ่มนี้จะดูเหมือนกดไม่ติด
- โหมดใหม่เปิดไม่ขึ้นจะถอยกลับไปโหมดเดิมแล้วขึ้นข้อความ ไม่ปล่อยให้กล้องค้างดับ

#### ปักกล้องด้วยชื่อรุ่น ไม่ใช่ index

`CAMERA_USB_NAME` รับ**บางส่วนของชื่อ** ไม่สนตัวพิมพ์เล็ก-ใหญ่ (`c922` ก็พอ)
ดีกว่า `CAMERA_USB_INDEX` เพราะ index สลับกันเองเวลาถอด-เสียบหรือรีบูต ส่วนชื่อรุ่นไม่สลับ
ตั้งชื่อไว้แล้วหาไม่เจอจะ**ฟ้องพร้อมรายชื่อกล้องที่เจอ** ไม่ใช่เงียบ ๆ ไปเปิดกล้องตัวอื่นให้

ดูว่าเครื่องเห็นกล้องอะไรบ้าง:

```bash
python -c "import camera; print(camera.capture_devices())"
# [(0, 'Integrated Camera'), (1, 'c922 Pro Stream Webcam')]
```

#### ขนาดภาพ — ถามกล้องเอา ไม่ต้องกรอกเอง

`CAMERA_AUTO_SIZE=true` (ค่าเริ่มต้น) จะถามไดรเวอร์ว่ากล้องรองรับโหมดอะไรบ้าง
แล้วเลือกให้เอง — บนเครื่องทดสอบได้ 36 โหมดใน 0.16 วินาที โดยไม่เปิดสตรีมเลย

```bash
python -c "import camera; print(camera.capture_modes(0))"
```

เกณฑ์การเลือก เรียงตามลำดับ

1. **สัดส่วนกว้างที่สุดที่กล้องมี** มาก่อนความละเอียด
2. ต้องส่งภาพได้ถึง `CAMERA_FPS`
3. เลือกอันที่พิกเซลเยอะสุดที่เหลือ

ข้อ 1 มาก่อนข้อ 3 เพราะโหมด 4:3 บนเซนเซอร์ 16:9 คือภาพที่**ถูกตัดขอบซ้าย-ขวาทิ้ง**
วัดกับ C922 ด้วยการจับคู่ภาพระหว่างสองโหมด: 640×480 ตรงกับส่วนกลางของ 1280×720
ที่ x=157 (ทฤษฎีทำนายไว้ 160) — มุมนอนหายไป 25% เหลือ 56° จาก 70°
และการยอมเสียพิกเซลไม่ได้ทำให้หน้าคนเล็กลงด้วยซ้ำ: 864 พิกเซลบน 70° = 12.3 px/องศา
ซึ่ง**ละเอียดกว่า** 640 พิกเซลบน 56° (11.4)

| `CAMERA_FPS` ที่ขอ | โหมดที่ถูกเลือกให้ (C922) |
|---|---|
| 10 | 1280×720 |
| 15 | 1024×576 |
| 20 | 864×480 |
| 25 ขึ้นไป | 800×448 |

⚠️ **"ไม่กำหนดขนาดเลย" ไม่ใช่ทางเลือกที่ดี** — ค่า default ที่เว็บแคมให้มาเมื่อไม่สั่งอะไร
คือ 640×480 (วัดแล้วทั้ง DirectShow และ Media Foundation) ซึ่งเป็นโหมด 4:3 ที่แคบที่สุด
การ "ไม่เลือก" จึงเท่ากับเลือกโหมดที่ตัดมุมมองทิ้งมากที่สุด

⚠️ **การลองตั้งขนาดแล้วอ่านกลับใช้ตรวจไม่ได้** — `cap.set()` แล้ว `cap.get()` ตอบตามที่ขอเสมอ
ไม่ว่ากล้องจะทำได้จริงหรือไม่ (ขอ 864×480 กับ 1920×1080 ตอบกลับตรงทั้งคู่ ทั้งที่
ความเร็วจริงต่างกันหกเท่า) จึงต้องถามไดรเวอร์ตรง ๆ ผ่าน `IAMStreamConfig::GetStreamCaps`

ระบบที่ถามไม่ได้ (Linux/Pi · macOS) จะถอยไปใช้ `CAMERA_WIDTH`/`CAMERA_HEIGHT` ตามเดิม

#### Windows: ทำไมค่า `CAMERA_API` ถึงสำคัญ

`CAMERA_API=auto` บน Windows แปลว่า **DirectShow** ไม่ใช่ "ปล่อยให้ OpenCV เลือก"
เพราะทางที่ OpenCV เลือกเอง (Media Foundation) มีปัญหาสองข้อที่วัดได้บนเครื่องจริง

| กล้อง | Media Foundation | DirectShow |
|---|---|---|
| Logitech C922 | **มองไม่เห็นเลย** — เปิดไม่ได้ | เปิดได้ใน 0.5 วินาที |
| กล้องในตัวโน้ตบุ๊ก (Chicony) | เปิดได้ แต่ใช้ **84 วินาที** | มองไม่เห็น |

เว็บแคม USB ที่ "เสียบอยู่แต่โปรแกรมบอกว่าเปิดไม่ได้" บน Windows มักเป็นข้อแรกนี้
ถ้ากล้องตัวไหนมีแต่ Media Foundation ที่เห็น โปรแกรมจะถอยไปใช้ให้เองพร้อมเตือนก่อน
ว่าอาจใช้เวลาสักครู่ (จะได้ไม่ดูเหมือนค้าง) หรือจะสั่งตรง ๆ ด้วย `CAMERA_API=msmf` ก็ได้

### ต่างกันตรงไหน

| | ห้องรวม | รายบุคคล | เฉพาะคนในรูป |
|---|---|---|---|
| รายงานเป็น | ค่าเดียวของทั้งห้อง | แยกทีละคน | แยกทีละคน **เฉพาะคนที่มีรูป** |
| id บนหน้าจอ | **ไม่แสดงเลย** | `#3` ต่อกรอบ | ชื่อคน (`?` = เดา) |
| ลายเซ็นโครงหน้า | **ไม่คำนวณเลย** | คำนวณและเก็บใน RAM | คำนวณเพื่อเทียบกับรูป **แต่ไม่เก็บเป็น pool** |
| **การวัดตา** (EAR · กะพริบ · ง่วง) | **ไม่วัดเลย** | วัดครบ | วัดครบ |
| re-ID (จำคนที่กลับมา) | ปิดถาวร | เปิด | ปิด — ความเป็นคนเดิมมาจาก**รูป** |
| คอลัมน์ `person` | `None` เสมอ | หมายเลขคน | หมายเลขคน + `name` |
| คนที่ไม่มีรูป | – | บันทึกด้วย (`name` = `null`) | ขึ้นกับ `FACES_GUESS` (ดูด้านล่าง) |
| payload | `to_room_row()` | `to_focus_row()` | `to_focus_row()` |

โหมดห้องรวมเป็นค่าเริ่มต้นเพราะ**ตอบคำถามของโครงงานได้ครบโดยไม่ต้องแตะข้อมูลชีวมิติเลย**
คำถามคือ "อากาศในห้องแบบนี้ส่งผลกับสมาธิของคนในห้องไหม" ซึ่งไม่ต้องรู้ว่าใครเป็นใคร

**ทำไมโหมดห้องรวมไม่วัดตา** — การกะพริบตาและความง่วงเป็นสภาวะของ*ร่างกายรายบุคคล*
ไม่ใช่ค่าของ*ห้อง* และการหาค่า EAR ต้องซูมเข้าไปที่ดวงตาของแต่ละคน ซึ่งละเอียดเกินกว่า
ที่โหมดนี้ควรทำ ในโหมดห้องรวมระบบจึง**ไม่เรียก `average_ear()` แม้แต่ครั้งเดียว**
(`test_room_smoke.py` ดักการเรียกฟังก์ชันนี้ไว้เพื่อยืนยันทุกครั้งที่รันเทส)
ค่าที่เกี่ยวกับตาจะเป็น `None`/`0` — เป็น "ไม่ได้วัด" ไม่ใช่ "วัดแล้วได้ศูนย์"

### โหมดห้องรวมวัดอะไร

| ค่า | ความหมาย | ทำไมวัดแบบนี้ |
|---|---|---|
| **occupancy** | จำนวนคนแบบ**มัธยฐาน**ตลอดหน้าต่าง | ค่าสูงสุดกระโดดตามใบหน้าที่ตรวจเจอแวบเดียว มัธยฐานไม่กระโดด · เอาไปเทียบกับ CO₂ ได้ตรง ๆ |
| **movement_per_person_per_min** | อัตราการหันหน้า **หารด้วยจำนวนคน** | ห้อง 30 คนย่อมขยับรวมมากกว่าห้อง 5 คนโดยที่สมาธิไม่ได้แย่กว่า — ถ้าไม่หาร จะเทียบข้ามคาบไม่ได้เลย |
| **attention_ratio** | สัดส่วนการวัดที่หน้าอยู่กลาง | คำนวณจาก**การหันหน้าอย่างเดียว** ไม่เกี่ยวกับดวงตา · นับเฉพาะคนที่ calibrate เสร็จแล้ว คนที่ยังไม่เสร็จไม่มี neutral ให้เทียบ จะถูกนับเป็น "มองตรง" ทั้งที่ยังไม่รู้ |

`attention_ratio` เป็น `None` ไม่ใช่ `0.0` เมื่อยังไม่มีใครให้วัด — ต่างกันมาก
`0.0` แปลว่าไม่มีใครมองตรงเลย ส่วน `None` แปลว่ายังไม่รู้

> เกณฑ์ `WINDOW_MOVEMENT_THRESHOLD` ในโหมดห้องรวมเทียบกับ**อัตราต่อคน** ไม่ใช่ผลรวม
> ไม่งั้นห้องที่คนเยอะจะขึ้นว่าเกินเกณฑ์เสมอ

## ตรวจจับอะไรได้บ้าง

รองรับ **หลายคนพร้อมกัน** (ค่าเริ่มต้น 6 คน) โดยแยกวิเคราะห์รายบุคคล

| ค่า | ความหมาย | ที่มา |
|---|---|---|
| **face_count** | จำนวนใบหน้าในเฟรม | MediaPipe |
| **usable** | จำนวนใบหน้าที่ใหญ่พอจะวัดได้น่าเชื่อถือ | `analyzer.py` |
| **person** | หมายเลขคน (จากการติดตามตำแหน่ง ไม่ใช่การจำหน้า) | `tracker.py` |
| **direction** | ทิศที่หัน `Left` / `Right` / `Up` / `Down` พร้อมจำนวนครั้ง | `analyzer.py` |
| **movement** | ผลรวมจำนวนครั้งที่หันหน้าใน 15 วินาที | `analyzer.py` |
| **blink score** ¹ | คะแนนการหลับตา 0–1 (จาก blendshape หรือ EAR) | `analyzer.py` |
| **blink rate** ¹ | อัตราการกะพริบต่อนาที (ปกติ 8–21) | `analyzer.py` |
| **drowsy** ¹ | หลับตานานเกิน 1.2 วินาที = ง่วง (ไม่ใช่แค่กะพริบ) | `analyzer.py` |
| **quality** | 0–1 · ใบหน้าเล็กเกินไป = ค่าที่วัดได้เชื่อถือไม่ได้ | `analyzer.py` |
| **emotion** ¹ | การแสดงออกบนใบหน้า: `happy` `sad` `surprised` `angry` `neutral` | `emotion.py` |
| **name** ¹ | ชื่อคน ถ้าตรงกับรูปใน `faces/` · `None` = ไม่รู้ | `faces.py` |
| **posture** ² | `standing` · `sitting` · `lying` | `body.py` |
| **gesture** ² | ยกมือ · โบกมือ · กอดอก · เท้าเอว · ชี้ | `body.py` |
| **phone** ² | กำลังใช้โทรศัพท์อยู่ไหม (นับเฉพาะเครื่องที่อยู่ในระยะมือ) | `phone.py` |

¹ **เฉพาะโหมดรายบุคคล** — โหมดห้องรวมไม่วัดตาเลย ค่าเหล่านี้จะเป็น `None`/`0`
² **เฉพาะโหมดติดตามกิจกรรม** (เมนูข้อ 1) — โหมดอื่นไม่โหลดโมเดลพวกนี้เลย

## สี่อย่างที่ทำให้แม่นขึ้นเมื่อมีหลายคน

> หัวข้อ 1–2 ว่าด้วยการวัดตา จึงใช้กับ**โหมดรายบุคคล**เท่านั้น
> หัวข้อ 3–4 ใช้กับทั้งสองโหมด

### 1. blendshape แทน EAR เรขาคณิต

MediaPipe ให้คะแนน `eyeBlinkLeft` / `eyeBlinkRight` ที่โมเดลเรียนรู้มาแล้วว่ารูปตาแต่ละแบบ
หน้าตาเป็นอย่างไร จึง**ไม่ต้อง calibrate รายคน** และทนต่อการหันหน้าและการใส่แว่นได้ดีกว่า
EAR ที่คำนวณจากระยะเปลือกตาตรง ๆ

ตั้ง `BLINK_METHOD=auto` (ค่าเริ่มต้น) จะใช้ blendshape ถ้ามี ไม่งั้นถอยไป EAR อัตโนมัติ

### 2. EAR baseline รายบุคคล

ถ้าใช้วิธี EAR ระบบจะ**เรียนค่า EAR ตาเปิดของแต่ละคน**ตอน calibrate
แล้วตั้งเกณฑ์เป็นสัดส่วนของค่านั้น (`ตาเปิด × 0.65`)

จำเป็นมากเมื่อมีหลายคน เพราะ**คนตาโตกับคนตาเล็กให้ค่า EAR ต่างกันได้เกิน 2 เท่า**
เกณฑ์ตายตัว 0.18 ที่เหมาะกับคนหนึ่ง จะทำให้อีกคน "กะพริบตลอดเวลา" หรือ "ไม่เคยกะพริบเลย"

ใช้เปอร์เซ็นไทล์ที่ 75 ไม่ใช่ค่าเฉลี่ย เพราะระหว่าง calibrate ผู้ใช้ย่อมกะพริบตาบ้าง

### 3. quality gating — ไม่รายงานค่าที่วัดไม่ได้

EAR คำนวณจากระยะเปลือกตาซึ่งเล็กมาก (~8% ของระยะระหว่างหางตา)
ถ้าคนอยู่ไกลจนใบหน้าเล็ก ระยะนั้นจะเหลือไม่กี่พิกเซลจนสัญญาณรบกวนกลบข้อมูลจริง

ระบบจึงวัด **ระยะระหว่างหางตาเป็นพิกเซล** แล้ว**ตัดใบหน้าที่ต่ำกว่า 40 px ออกจากการวิเคราะห์**
(ยังนับใน `face_count` อยู่ แต่ไม่เอาไปคิด EAR/direction) บนหน้าจอจะขึ้นว่า `too far`

> นี่คือความแม่นยำในความหมายที่สำคัญที่สุด — **ไม่รายงานตัวเลขที่ตัวเองก็รู้ว่าเชื่อไม่ได้**

### 4. tracker ที่ไม่สลับ id

เมื่อมีหลายคน ปัญหาใหญ่ที่สุดคือ id สลับกันตอนคนเดินไขว้ ระบบใช้สามอย่างร่วมกัน

| กลไก | แก้ปัญหาอะไร |
|---|---|
| **ทำนายตำแหน่งจากความเร็ว** | คนที่กำลังเดินถูกจับคู่ถูกตัวแม้ขยับไปไกลระหว่างเฟรม |
| **cost ผสม** (ระยะ + IoU + ขนาด) | ขนาดใบหน้าช่วยแยกคนใกล้กล้องออกจากคนไกล แม้ตำแหน่งบนภาพใกล้กัน |
| **swap guard** | หลังจับคู่เสร็จ ตรวจว่าถ้าสลับคู่แล้ว cost รวมดีขึ้นไหม — แก้กรณีที่ greedy ตัดสินใจผิด |

#### เมื่อคนขยับเยอะแล้ว id หลุด

วัดกับชุดสถานการณ์การเคลื่อนไหว 144 แบบ (เดินคงที่ · เดินแล้วกลับตัว · ขยับอยู่กับที่
× ความเร็ว × จำนวนเฟรมที่ตรวจไม่เจอ × มี/ไม่มีคนอื่นในเฟรม) พร้อมเกณฑ์ความปลอดภัย
สองตัวที่ดึงกันคนละทาง เพราะการแก้ให้ id ไม่แตกนั้นทำได้ง่ายมากถ้ายอมให้จับคู่มั่ว

| | เดิม | ตอนนี้ |
|---|---|---|
| คนขยับเยอะแล้วยังเป็น id เดิม | 37% | **47%** |
| สองคนเดินสวนกันแล้ว id ไม่สลับ | 66% | **100%** |
| คนใหม่ไม่สวมรอย id คนที่เพิ่งออกไป | 100% | 100% |

(ที่ 15fps · เฟรมถี่ขึ้นดีขึ้นอีก: ที่ 20fps เป็น 69% · ดูตาราง fps ด้านล่าง)

สามอย่างที่แก้:

1. **นาฬิกาของแต่ละคน** — เดิมคิด `dt` เดียวจาก track ที่เพิ่งเห็นล่าสุดแล้วใช้กับทุกคน
   ผลคือถ้ามีใครนั่งนิ่งให้เห็นทุกเฟรม `dt` จะเท่ากับหนึ่งเฟรมเสมอ แล้วคนที่หายไป
   เป็นวินาทีก็ถูกทำนายล่วงหน้าแค่หนึ่งเฟรม ทั้งที่เขาเดินมาทั้งวินาที
   ยิ่งห้องมีคนนั่งอยู่ด้วยยิ่งพลาด — คนที่นั่งนั่นแหละที่กด `dt` ของทุกคน
2. **IoU คิดจากกรอบที่เลื่อนตามการทำนายแล้ว** — เดิมระยะทางวัดจากตำแหน่งที่ทำนาย
   แต่ IoU วัดจากกรอบที่เห็นครั้งล่าสุด สองสัญญาณจึงขัดกันเอง คนที่เดินเร็วพอให้
   กรอบสองเฟรมไม่ทับกันได้ IoU = 0 คือโดนลงโทษเต็มที่ ทั้งที่การทำนายชี้ถูกแล้ว
3. **ขอบฟ้าของการทำนาย** (`TRACKER_PREDICT_HORIZON`, 0.10 วินาที) — ความเร็วมาจาก
   ผลต่างตำแหน่งสองเฟรมซึ่งมี noise ติดมา คูณด้วย `dt` ยาว ๆ คือการขยาย noise นั้น
   และคน**ที่หยุดเดิน**ตอนที่ตรวจไม่เจอจะถูกทำนายว่าไปไกลลิบ พ้นขอบฟ้าแล้วจึงถือว่า
   เขาอยู่ที่เดิม ซึ่งเดาผิดน้อยกว่าเดาว่าเดินต่อ

#### ⚠️ ทางที่ดูน่าจะได้ผลแต่วัดแล้วว่าแย่กว่า

"คนที่หายไปนานกว่าย่อมไปได้ไกลกว่า จึงควรผ่อนวงจับคู่ให้กว้างขึ้นตามเวลา"
ฟังดูสมเหตุสมผลและ**ได้ผลจริงกับตัวเลขแรก** (รักษา id 47% → 72%) แต่วงที่กว้างขึ้น
ไม่รู้จักแยกว่า "คนเดิมที่เดินไป" กับ "คนใหม่ที่เพิ่งเดินเข้ามา" ต่างกันตรงไหน
ผลคือ **คนใหม่สวมรอย id ของคนที่เพิ่งออกไป 92% ของกรณี** (จาก 0%)
ซึ่งทำให้ข้อมูลผิดหนักกว่าปัญหาที่ตั้งใจแก้มาก

ยังเปิดได้ด้วย `TRACKER_GATE_DRIFT` / `TRACKER_MAX_GATE` ถ้ารู้แน่ว่าจะมีคนเดียว
ในเฟรมเสมอ (ไม่มีใครให้สวมรอย) — ปิดไว้เป็นค่าเริ่มต้น

#### ภาพเบลอตอนขยับ — แก้ที่ชัตเตอร์ ไม่ใช่ที่โค้ด

อาการ "ขยับแล้วหน้าหลุดการติดตาม" ส่วนหนึ่งไม่ใช่ปัญหาของตัวติดตามเลย แต่เป็นเพราะ
**ตรวจไม่เจอหน้าตั้งแต่แรก** เมื่อภาพเบลอ ซึ่งเกิดที่เซนเซอร์ ซอฟต์แวร์กู้คืนไม่ได้

วัดด้วยการใส่ภาพเบลอแนวนอนทีละระดับลงในรูปใบหน้าจริง แล้วดูว่าแต่ละขั้นตอนตายที่ไหน

| ใบหน้ากว้าง | ตัวตรวจจับตายที่ | **FaceLandmarker ตายที่** |
|---|---|---|
| 70 px | 60 px | อ่านไม่ออกตั้งแต่ยังไม่เบลอ |
| 100 px | 54 px | **22 px** |
| 150 px | 58 px | **46 px** |
| 200 px | 60 px | **58 px** |
| 260 px | 60 px | **60 px** |

สองอย่างที่อ่านได้จากตารางนี้

1. **FaceLandmarker คือคอขวด ไม่ใช่ตัวตรวจจับ** — ตัวตรวจจับยังเห็นกรอบหน้าอยู่
   ที่ระดับเบลอซึ่ง landmarker อ่านอะไรไม่ออกแล้ว อาการที่เห็นคือ "ยังมีกรอบ
   แต่ค่าทุกอย่างหาย"
2. **ความทนทานแปรตามขนาดใบหน้า** ราว 25–30% ของความกว้างใบหน้า คนที่นั่งไกล
   จึงหลุดง่ายกว่ามาก ทั้งที่ขยับเท่ากัน

ชัตเตอร์ที่กล้องเลือกเองในแสงห้องคือ 1/32 วินาที · ใบหน้ากว้าง 100 px ที่เคลื่อนที่
1 ความกว้างเฟรมต่อวินาที เบลอ 27 px ซึ่ง**เกินเพดาน 22 px ไปแล้ว**

ตั้งชัตเตอร์เองแก้ตรงนี้ได้เกือบฟรี — วัดกับ C922 ในแสงห้องจริง

| | สว่าง | noise | SNR | เบลอเทียบกับเดิม |
|---|---|---|---|---|
| กล้องปรับเอง (1/32s) | 111.6 | 2.29 | 48.8 | 1× |
| **1/128s + gain 255** | **110.0** | **2.49** | **44.2** | **¼×** |
| 1/256s + gain 255 | 75.7 | 5.89 | 12.8 | ⅛× (พังแล้ว) |

ความสว่างเท่าเดิม SNR ลดลง 9% แต่ภาพเบลอเหลือหนึ่งในสี่ ตั้งด้วย `CAMERA_EXPOSURE`
กับ `CAMERA_GAIN`

⚠️ **ค่านี้ผูกกับแสงในห้องที่วัด** ย้ายที่หรือปิดไฟแล้วภาพจะมืด — ลบทิ้งเพื่อกลับไป
ให้กล้องปรับเอง หรือขยับขึ้นหนึ่งสต็อป (`-6`) แล้ววัดใหม่

#### เฟรมถี่ขึ้นช่วยเรื่องนี้ตรง ๆ

คนขยับได้น้อยลงระหว่างสองเฟรม ตัวจับคู่จึงงานง่ายขึ้น — เป็นตัวแปรเดียวที่ดีขึ้น
โดยไม่ต้องแลกอะไรเลย

| fps | รักษา id | ไม่สลับ id | ไม่ถูกสวมรอย |
|---|---|---|---|
| 15 | 47% | 100% | 100% |
| 20 | 69% | 77% | 100% |
| 30 | 72% | 88% | 100% |

### (ทางเลือก) head pose เป็นองศาจริง

ตั้ง `MODEL_TRANSFORM_MATRIX=true` และ `POSE_METHOD=matrix` จะได้มุมหันหน้าเป็น**องศาจริง**
จาก facial transformation matrix ซึ่งแม่นกว่าการประมาณจากตำแหน่งจมูกเมื่อหันมาก ๆ

> ⚠️ **ต้องยืนยันทิศบนหน้าจอก่อนใช้จริง** — แกนอ้างอิงของ MediaPipe อาจให้เครื่องหมาย
> กลับด้านกับที่คาด ถ้าหันขวาแล้วขึ้น `LEFT` ให้ตั้ง `POSE_MATRIX_INVERT_YAW=true`
> ค่าเริ่มต้นยังเป็น `geometric` เพราะผ่านการทดสอบแล้ว

## จำคนจากรูป — วางรูปในโฟลเดอร์ `faces/`

เดิมระบบแจกหมายเลขให้ทุกคนที่เห็น (`#1`, `#2`) และเดินออกจากเฟรมแล้วกลับมาก็ได้เลขใหม่
ถ้าอยากให้ข้อมูลผูกกับคนจริง ให้วางรูปไว้แล้วตั้งชื่อไฟล์เป็นชื่อคน:

```
pi-vision/faces/สมชาย.jpg
pi-vision/faces/Nok.png
pi-vision/faces/Ann/1.jpg      ← โฟลเดอร์ต่อคน ใส่หลายรูปได้ (แม่นกว่ามาก)
pi-vision/faces/Ann/2.jpg
```

- **โฟลเดอร์ว่าง = ทุกอย่างเหมือนเดิม** ใช้หมายเลขต่อไป · ฟีเจอร์นี้เปิดตัวเองเมื่อมีรูป
- วางรูปเพิ่มระหว่างที่โปรแกรมทำงานได้ ระบบอ่านใหม่เองภายใน ~20 วินาที (`FACES_RESCAN_SECONDS`)
- หนึ่งรูปควรมีใบหน้าเดียว หันตรง เห็นชัด · รูปที่หาใบหน้าไม่เจอจะถูกข้ามและแจ้งบน console
- **หลายรูปต่อคนแม่นกว่ารูปเดียวอย่างมีนัย** ด้วยเหตุผลเดียวกับที่ tracker เฉลี่ยหลายเฟรม:
  ค่าเฉลี่ยลด noise ลงตาม √N · และเป็นข้อมูลที่ระบบใช้**ตั้งเกณฑ์เอง** (หัวข้อถัดไป)
- **รูปหน้าตรงยังใช้เป็นจุดศูนย์ของการวัดการหันหน้าด้วย** — คนที่มีรูปจึงไม่ต้องนั่ง
  calibrate ตอนเริ่ม ดูหัวข้อ [calibrate ท่านิ่ง](#-calibrate-ท่านิ่ง--ต้องเข้าใจก่อนใช้)

### ถ่ายรูปลงทะเบียนจากกล้องสด — กด `n`

ไม่ต้องหารูปจากที่อื่นมาวางแล้ว · กด `n` ขณะโปรแกรมทำงาน แล้ว:

1. **พิมพ์ชื่อ** (a–z 0–9 `-` `_` — ชื่อนี้กลายเป็นชื่อโฟลเดอร์ จึงพิมพ์ไทยไม่ได้)
2. **ยืนให้เป็นคนที่อยู่ใกล้กล้องที่สุด** — มุมเล็งสีฟ้าบนจอบอกว่ากำลังเล็งใคร
   และกรอบบาง ๆ รอบนอกคือ**ขอบเขตที่จะถูกบันทึกจริง**
3. **เคาะ `space`** ทีละใบ · ควรถ่าย 2–3 ใบ เปลี่ยนมุมนิดหน่อยระหว่างใบ
4. **`Esc`** จบ — ระบบอ่านรูปใหม่ให้ทันที ไม่ต้องรอรอบ 20 วินาทีและไม่ต้องรีสตาร์ต

รูปถูกเก็บที่ `faces/<ชื่อ>/cam_<วันเวลา>.jpg` · พิมพ์ชื่อที่มีอยู่แล้วคือการ**เพิ่มรูป
ให้คนเดิม** (แผงล่างจอบอกว่ามีอยู่กี่ใบแล้ว — ระวังพิมพ์ `donut` กับ `Donut` ซึ่งเป็น
คนละคนเพราะเป็นคนละโฟลเดอร์)

**ระบบจะไม่ยอมถ่ายให้ในสามกรณี** และบอกเหตุผลบนจอทุกครั้ง:

| บนจอขึ้นว่า | แปลว่า | ทำยังไง |
|---|---|---|
| `no face in frame` | ยังไม่เห็นใบหน้าใคร | เข้ามาในเฟรม |
| `face 8% of frame — need 12%` | ยืนไกลไป ครอปมาแล้วจะเล็กจนหาหน้าไม่เจอ | เดินเข้ามาใกล้ |
| `another face is too close` | มีหน้าคนอื่นชิดจนตัดออกจากรูปไม่ได้ | ถ่ายทีละคน |

⚠️ **ทำไมต้องตัดคนอื่นออกจากรูป** — ตัวอ่านรูปลงทะเบียนอ่านได้ **หนึ่งใบหน้าต่อรูป**
(`num_faces=1`) ถ้ามีคนอื่นติดมาด้วย มันเลือกหน้าเองโดยไม่บอกใคร · วัดกับรูปจริง:
วางคนสองคนไว้ในเฟรม เล็งที่คนซ้ายซึ่งใหญ่กว่า แล้วบันทึกทั้งเฟรม — ลายเซ็นที่ได้
ห่างจากคนที่เล็งไว้ `0.033` แต่ห่างจาก**คนที่ยืนข้าง ๆ** แค่ `0.007` คือมันเรียนหน้า
ของคนผิดไปเต็ม ๆ โดยไม่มี error อะไรเลย · โปรแกรมจึงหดกรอบครอปลงทีละขั้น
(ส่วนเผื่อ 0.6 → 0.15) จนคนอื่นหลุดออกไปก่อนบันทึกเสมอ หดจนสุดแล้วยังไม่พ้นถึงจะยอมแพ้

กรอบครอปมี**อัตราส่วนเท่าเฟรมของกล้อง**เสมอ ลายเซ็นจากรูปนี้จึงตรงกับที่อ่านจาก
ภาพสดพอดี (วัดได้ว่าห่างกัน `0.0000`) — เหตุผลอยู่ที่หัวไฟล์ `roi.py`

### สิ่งที่วิธีนี้ทำได้และทำไม่ได้

เทียบด้วย **ลายเซ็นโครงหน้า 8 ค่า** (`landmarks.face_signature`) ตัวเดียวกับที่ใช้จำ id
ในเซสชัน ไม่ใช่ face embedding แบบระบบยืนยันตัวตน:

- แยกคนที่โครงหน้าต่างกันได้ (สมาชิกบ้านเดียวกัน 2–5 คน)
- **พี่น้องหน้าคล้ายกันอาจแยกไม่ออก** — กรณีนี้ระบบจะ**ไม่เดา** และกลับไปใช้หมายเลข
  เพราะการติดชื่อผิดคนทำให้ข้อมูลสองคนปนกันโดยไม่มีใครรู้ ซึ่งแย่กว่าการไม่รู้ชื่อ
- ไม่ใช่ระบบความปลอดภัย · อย่าใช้ตัดสินใจอะไรที่สำคัญ

### เกณฑ์ตั้งเองจากชุดรูป (`FACES_AUTO_THRESHOLD` — เปิดไว้)

เกณฑ์ว่า "ใกล้แค่ไหนถึงนับว่าเป็นคนนี้" ไม่ได้ตั้งไว้ตายตัวอีกแล้ว ระบบวัดจาก
**ชุดรูปของคุณเอง** ทุกครั้งที่อ่านรูป (ตอนเริ่ม และทุกครั้งที่มีรูปเพิ่ม/ลบ):

| วัดอะไรจากรูป | ใช้ทำอะไร |
|---|---|
| รูปของคนเดียวกันห่างกันแค่ไหน | เกณฑ์ต้องอยู่**เหนือ**ค่านี้ ไม่งั้นจำคนของตัวเองไม่ได้ |
| คู่คนที่หน้าใกล้กันที่สุดห่างแค่ไหน | เกณฑ์ต้องอยู่**ใต้**ค่านี้ ไม่งั้นเริ่มติดชื่อผิดคน |

แล้ววางเกณฑ์ไว้กลางช่องว่างระหว่างสองค่านั้น ผลจะถูกพิมพ์ออก console ตอนเริ่ม:

```
[pi-vision] จำได้ 3 คนจากรูปใน faces/: Ann, Bee, Cee
[pi-vision] เกณฑ์ความเหมือน 0.042 — คำนวณจากรูป: รูปคนเดียวกันห่าง 0.036 · คนละคนใกล้สุด 0.084 (Ann·Cee)
```

- **รูปเบลอ/มุมแปลก → เกณฑ์กว้างขึ้นเอง** และ **คนหน้าคล้ายกันในแกลเลอรี → เกณฑ์แคบลงเอง**
  ทั้งสองอย่างนี้เดิมต้องมานั่งปรับ `FACES_THRESHOLD` เอาเองโดยไม่มีตัวเลขอ้างอิง
- ชุดรูปที่**แยกสองคนไม่ออก** (รูปคนเดียวกันห่างกันพอ ๆ กับที่สองคนนั้นต่างกัน) จะได้
  คำเตือนระบุชื่อคู่นั้น และเกณฑ์จะถูกกดลงจน**ไม่มีใครในคู่นั้นได้ชื่อแบบมั่นใจ** —
  ตั้งใจให้เป็นแบบนั้น เพราะคำตอบที่ "มั่นใจ" จากรูปที่แยกไม่ออกคือการเดาจากเสียงรบกวน
- **คนเดียวรูปเดียว = วัดอะไรไม่ได้เลย** ระบบจะใช้ `FACES_THRESHOLD` ตามเดิมและบอกเหตุผล
  · ใส่รูปเพิ่มอีกใบต่อคน แล้วมันจะเริ่มคำนวณเองได้

**สิ่งที่การ calibrate นี้ทำไม่ได้:** รูปบอกได้แค่ว่ารูปด้วยกันเองห่างกันแค่ไหน มันไม่รู้จัก
กล้องตัวที่จะใช้จริง แสงในห้องนั้น หรือระยะที่คนนั่ง — `FACES_AUTO_SPREAD` คือส่วนเผื่อ
สำหรับข้อนั้น ถ้าใช้จริงแล้วชื่อขึ้น `?` บ่อยทั้งที่เป็นคนในรูป ให้เพิ่มค่านี้ (หรือถ่ายรูป
ลงทะเบียนด้วยกล้องตัวเดียวกับที่ใช้จริง ซึ่งได้ผลกว่า)

ปิดได้ด้วย `FACES_AUTO_THRESHOLD=false` แล้วกลับไปใช้ `FACES_THRESHOLD` ตายตัวเหมือนเดิม
· `FACES_RATIO` (ratio test) ไม่ได้ถูกคำนวณเอง ยังปรับมือตามเดิม

## โหมดเฉพาะคนในรูป (`--mode known`)

สำหรับกรณีที่ต้องการข้อมูลของ**คนกลุ่มที่ระบุไว้ล่วงหน้า**เท่านั้น เช่นวัดสมาธิของ
นักเรียนในห้องที่ขออนุญาตแล้ว โดยไม่เก็บอะไรของคนอื่นที่เดินผ่านกล้อง

วิธีใช้: วางรูปใน `faces/` ตั้งชื่อไฟล์เป็นชื่อคน แล้วรัน `--mode known`

**สองข้อที่โหมดนี้ต่างจากโหมดรายบุคคล**

1. **ความเป็นคนเดิมมาจากรูป ไม่ใช่จากความจำของโปรแกรม** — re-ID ปิดอยู่ จึงไม่มี pool
   ลายเซ็นของคนแปลกหน้าค้างใน RAM เลย ลายเซ็นถูกคำนวณเพื่อเทียบกับรูปแล้วทิ้งไปกับ track
2. **คนที่ไม่มีรูปไม่ถูกบันทึก** ไม่ใช่บันทึกโดยไม่มีชื่อ — และการหันหน้าของเขาก็ไม่ถูก
   นับรวมเข้าแถวของคนที่มีชื่อด้วย (ไม่งั้นพฤติกรรมของคนแปลกหน้าจะไปอยู่ใต้ชื่อคนอื่น)
   ข้อนี้ต้องตั้ง `FACES_GUESS=false` เพราะการเดาจะติดชื่อให้ทุกคนที่เห็น ดูหัวข้อถัดไป

หน้าต่างเวลาที่ไม่มีคนรู้จักอยู่เลย = **ไม่มีแถวถูกส่ง** (ไม่ใช่แถวที่ `name` เป็น `null`)
— ข้อนี้เป็นจริงเมื่อ `FACES_GUESS=false` ดูหัวข้อถัดไป

> **`name` คือกุญแจที่นิ่ง ไม่ใช่ `person`** — โหมดนี้ปิด re-ID ฉะนั้นถ้าคนเดิมเดินออกไป
> แล้วกลับมา หมายเลข `person` จะเปลี่ยน แต่ `name` ยังเป็นค่าเดิม เวลาต่อกราฟรายคน
> ให้จัดกลุ่มด้วย `name`

ยังไม่มีรูปในโฟลเดอร์ โปรแกรมจะเตือนแล้วรันต่อ (ไม่บันทึกใครเลย) เพราะแกลเลอรีถูกอ่านซ้ำ
ทุก `FACES_RESCAN_SECONDS` — วางรูปทีหลังได้โดยไม่ต้องรีสตาร์ต

### เดา หรือ ยอมบอกว่าไม่รู้ (`FACES_GUESS`)

ค่าเริ่มต้นคือ **`true` = เดาคนที่ใกล้ที่สุดเสมอ** ไม่มีคำว่า `unknown` บนหน้าจอ

| | `FACES_GUESS=true` (ค่าเริ่มต้น) | `FACES_GUESS=false` |
|---|---|---|
| ตรงกับรูปชัดเจน | `somchai` | `somchai` |
| ใกล้ที่สุดแต่ไม่ผ่านเกณฑ์ | `somchai?` | `#3` |
| คนที่ไม่มีรูปเลย | ชื่อคนที่หน้าคล้ายที่สุด + `?` | `#3` |
| ในตาราง `focus` | ชื่อที่เดา **แยกจากชื่อที่มั่นใจไม่ได้** | `null` |
| คนแปลกหน้าในโหมด known | ถูกบันทึก**ใต้ชื่อคนอื่น** | ไม่ถูกบันทึก |

`?` บนหน้าจอหมายถึง "ใกล้ที่สุดเท่านี้ แต่ยังไม่ผ่านเกณฑ์" (ความหมายเดียวกับ `#5?`
ที่ใช้กับ id ชั่วคราวอยู่แล้ว) และชื่อที่ยังไม่มั่นใจจะถูก**เทียบใหม่ทุกเฟรม**
เพราะลายเซ็นนิ่งขึ้นเรื่อย ๆ — การล็อกคำเดาแรกไว้ตลอดกาลเท่ากับให้คำเดาตอนที่มี
ข้อมูลน้อยที่สุดเป็นคำตอบสุดท้าย ส่วนชื่อที่ผ่านเกณฑ์แล้วถือว่าจบ

> **สิ่งที่ต้องรู้ก่อนใช้ค่าเริ่มต้น:** การเดาไม่ได้ทำให้แม่นขึ้น มันย้ายความผิดพลาด
> จาก "ไม่มีชื่อ" (เห็นได้ แก้ได้ด้วยการเพิ่มรูป) ไปเป็น **"ชื่อผิด"** (มองไม่เห็นจาก
> ปลายทาง) ในฐานข้อมูลชื่อที่เดากับชื่อที่มั่นใจเป็นข้อความเหมือนกันเป๊ะ ฉะนั้นถ้าจะเอา
> ข้อมูลนี้ไปสรุปผลจริงจัง ให้ตั้ง `FACES_GUESS=false` · ถ้าใช้ดูสด ๆ บนจอ ค่าเริ่มต้น
> สะดวกกว่าเพราะได้ชื่อคนทันทีโดยไม่ต้องเทียบหมายเลขเอง
>
> ยังมีสองกรณีที่ยังตอบว่า "ยังไม่รู้" อยู่แม้เปิดการเดา คือ**ใบหน้าเล็กเกินเกณฑ์**
> และ**ลายเซ็นยังไม่นิ่ง** — ที่นั่นไม่มีข้อมูลให้เดา การเดาจะเป็นการสุ่มล้วน ๆ

## อารมณ์จากการแสดงออกบนใบหน้า

รายงาน `happy` · `sad` · `surprised` · `angry` · `neutral` โดยอ่านจาก **blendshapes**
ชุดเดียวกับที่ใช้ตรวจการหลับตาอยู่แล้ว — ไม่มีโมเดลเพิ่ม ไม่มี inference รอบที่สอง
ไม่มีภาระ CPU เพิ่มบน Pi

แต่ละอารมณ์คิดจาก**กล้ามเนื้อที่ต้องขยับร่วมกัน** ไม่ใช่ตัวเดียวโดด ๆ (ตัวเดียวเกิดจาก
การพูดหรือหันหน้าได้) แล้วกรองด้วยเสียงข้างมากในหน้าต่าง 12 เฟรม เพื่อไม่ให้ค่ากระโดด
ตอนพูดหรือกะพริบตา

**ขอบเขต:** นี่คือการอ่าน**การแสดงออก** ไม่ใช่ความรู้สึกข้างใน — คนยิ้มขณะเครียดก็ได้
`happy` · เมื่อไม่มีอะไรเด่นพอจะได้ `neutral` ซึ่งเป็นคำตอบ ไม่ใช่การไม่มีคำตอบ
ปิดได้ด้วย `EMOTION_ENABLED=false`

### จะเห็นมันตรงไหน

| ที่ | เห็นอะไร |
|---|---|
| ป้ายใต้กรอบใบหน้า | `somchai  happy  eye 0.12  mv 3` |
| แผง HUD มุมจอ | คอลัมน์อารมณ์ต่อคน |
| console ทุกหน้าต่างสรุป | `person=1 name=somchai emotion=happy faces=1 …` |
| ตาราง `focus` | คอลัมน์ `emotion` |

**หน้านิ่งขึ้นว่า `neutral` — ไม่ใช่ว่างเปล่า** เดิมซ่อน `neutral` ไว้เพื่อลดความรก
ผลคือคนที่นั่งหน้านิ่ง (ซึ่งเป็นเวลาส่วนใหญ่) ไม่เห็นอะไรเลย แล้วแยกไม่ออกว่าฟีเจอร์
ปิดอยู่ · พัง · หรือแค่ยังไม่มีอารมณ์ให้อ่าน ตอนนี้จึงแสดงทุกกรณี และช่องว่างหมายถึง
"ปิดไว้หรือไม่มี blendshapes" อย่างเดียว

**ปรับ threshold จากของจริง:** กด `e` ขณะรันเพื่อดูคะแนนดิบทั้งสี่ค่า
(`happy 0.62  surpr 0.11  angry 0.04  sad 0.01`) แล้วค่อยตั้ง `EMOTION_THRESHOLD`
ให้เข้ากับกล้องและแสงของห้องจริง ดีกว่าเดาจากค่าเริ่มต้น

cd pi-vision

pip install -r requirements.txt --break-system-packages

## ใช้งาน

```bash
python3 main.py                 # ถามโหมดก่อน แล้วเปิดหน้าต่างแสดงผล
python3 main.py --mode room     # ข้ามคำถาม ใช้โหมดห้องรวม
python3 main.py --mode person   # ข้ามคำถาม ใช้โหมดรายบุคคล
python3 main.py --mode known    # รู้จักเฉพาะคนที่มีรูปใน faces/
python3 main.py --no-window     # ไม่มีจอ (ผ่าน SSH) พิมพ์สรุปลง console
python3 main.py --source usb    # บังคับใช้ USB webcam
python3 main.py --source csi    # บังคับใช้ Camera Module 3
python3 main.py --mesh          # วาด landmark ครบ 468 จุด

python3 test_logic.py           # ทดสอบตรรกะ ไม่ต้องมีกล้อง
python3 test_room_smoke.py      # รันลูปหลักจริงด้วยกล้องปลอม ครบทั้งสามโหมด

```

**ปุ่มลัดขณะรัน**

| ปุ่ม | ทำอะไร |
|---|---|
| `q` / `Esc` | ออก |
| `c` | calibrate ท่านิ่งใหม่ทุกคนจากภาพสด (ทับค่าที่อ่านมาจากรูปด้วย) |
| `f` | **ลืมทุก id และลายเซ็นโครงหน้าทันที** (ความเป็นส่วนตัว) |
| `m` | สลับการวาด mesh |

| `v` | เมนูเลือกกล้อง |
| `r` | เมนูเลือกความละเอียด (รายการมาจากที่กล้องรองรับจริง) |
| `n` | **ถ่ายรูปลงทะเบียนคนใหม่จากกล้องสด** — พิมพ์ชื่อ แล้วเคาะ `space` ถ่าย (ดูหัวข้อถัดไป) |

## 🔑 calibrate ท่านิ่ง — ต้องเข้าใจก่อนใช้

ระบบต้องรู้ว่า "หน้าตรง" ของคุณให้ค่าเท่าไร แล้ววัดการหันเทียบกับจุดนั้น
จำเป็นเพราะโครงหน้าแต่ละคนไม่สมมาตร และกล้องมักไม่ได้อยู่ระดับตาพอดี —
ถ้าไม่หักค่านี้ออก ระบบจะคิดว่าคุณ "หันอยู่ตลอดเวลา"

**จุดศูนย์นั้นมาได้สองทาง:**

| | จากรูปใน `faces/` (ค่าเริ่มต้นถ้ามีรูป) | จากการนั่งนิ่ง (เดิม) |
|---|---|---|
| ต้องทำอะไร | ไม่ต้องทำอะไรเลย | นั่งมองตรงเข้ากล้อง 3 วินาที |
| เริ่มวัดได้เมื่อไร | ทันทีที่ระบบรู้ว่าคุณคือใคร | หลังครบเวลา |
| ใช้กับใคร | คนที่มีรูปลงทะเบียน | ทุกคนที่ไม่มีรูป |
| ถ้าตอนนั้นเผลอหันหน้าอยู่ | ไม่มีผล — จุดศูนย์มาจากรูป | **ท่าหันนั้นกลายเป็น "ตรง" ไปทั้งเซสชัน** |

แถวสุดท้ายคือเหตุผลหลักของการอ่านจากรูป ไม่ใช่แค่ความเร็ว: การ calibrate สด
เชื่อว่าคุณมองตรงอยู่จริงในสามวินาทีนั้น ถ้าคุณเดินเข้ามาแล้วหันไปคุยกับคนข้าง ๆ พอดี
ระบบจะจำท่าหันข้างเป็นจุดศูนย์ แล้วรายงานว่าคุณ "หันหน้า" ทุกครั้งที่คุณมองตรง —
โดยไม่มีอะไรบนหน้าจอบอกว่ากำลังผิด · ข้อนี้ยังกลับมาเกิดใหม่ทุกครั้งที่คุณได้ id ใหม่

ตอนเปิดโปรแกรมจะบอกว่าใครใช้ท่านิ่งจากรูปได้บ้าง:

```
[pi-vision] อ่านท่านิ่งจากรูปได้ 3 คน: Ann, Bee, Cee — คนกลุ่มนี้ไม่ต้องรอ calibrate
[pi-vision] ! ใช้รูปของ Dee เป็นจุดอ้างอิงท่านิ่งไม่ได้: รูปหันข้างอยู่ (yaw +0.213 เกิน 0.080) — …
```

- รูปที่**คนในรูปหันข้างอยู่**จะถูกปฏิเสธ (ไม่งั้นระบบจะจำท่าหันเป็นท่าตรง) ·
  แกน pitch ไม่มี "ศูนย์" ให้เทียบเพราะจมูกอยู่ต่ำกว่าแนวตาเป็นทุนเดิม จึงตรวจโดย
  เทียบกับ**มัธยฐานของคนอื่นในแกลเลอรี** และทำได้ต่อเมื่อมีคนตั้งแต่ 3 คนขึ้นไป
- **ถ่ายรูปลงทะเบียนด้วยมุมกล้องใกล้เคียงกับกล้องที่ใช้จริง** — ถ้ารูปทั้งชุดถ่ายจาก
  มุมกดลงมาแต่กล้องจริงอยู่ระดับตา ทุกคนจะมีจุดศูนย์ที่เพี้ยนไปทางเดียวกัน และ
  **ไม่มีอะไรในชุดรูปบอกได้** (การตรวจข้างบนจับได้แค่คนที่เพี้ยนต่างจากกลุ่ม)
- ใช้กับ `POSE_METHOD=geometric` (ค่าเริ่มต้น) เท่านั้น — วิธี `matrix` คิดเป็นองศา
  ซึ่งเป็นคนละหน่วยกับค่าที่อ่านจากรูป เอามาหักกันจะได้ตัวเลขที่ผิดแบบดูไม่ออก
- **จุดศูนย์เดินตามชื่อที่ระบบยกข้อมูลให้** — ได้ชื่อเมื่อไรก็ได้จุดศูนย์ของคนนั้นทันที
  แม้ยังเป็นชื่อที่เดา (`Ann?`) เพราะแถวในฐานข้อมูลก็ถูกบันทึกใต้ชื่อนั้นอยู่แล้ว
  การวัดด้วยจุดศูนย์ของคนอื่นจึงขัดกันเอง · ถ้าเดาผิด ความผิดพลาดคือผลต่าง bias
  ระหว่างสองคนซึ่งเล็กและมีขอบเขต ส่วนการ calibrate สดพลาดได้ไม่จำกัด
  (ท่าหันข้างกลายเป็นท่าตรงทั้งเซสชัน) · พอชื่อถูกแก้เป็นชื่อที่มั่นใจ จุดศูนย์ย้ายตามทันที
  · ตั้ง `FACES_GUESS=false` แล้วคนที่ไม่ผ่านเกณฑ์จะไม่มีชื่อ จึงกลับไป calibrate เองตามเดิม
- **EAR ตาเปิดยังเรียนจากภาพสดเสมอ** ไม่ได้อ่านจากรูป เพราะถ้าคนในรูปกำลังกะพริบพอดี
  เกณฑ์การกะพริบของเขาจะเพี้ยนทั้งเซสชัน · การเรียนสดมีหลายร้อยเฟรมให้หยิบเปอร์เซ็นไทล์
- ปิดได้ด้วย `POSE_NEUTRAL_FROM_PHOTOS=false`

กรอบใบหน้าจะเป็น **สีเทาพร้อมแถบความคืบหน้า** ระหว่าง calibrate สด
และเปลี่ยนเป็นสีเขียวเมื่อพร้อมใช้งาน (คนที่ใช้ท่านิ่งจากรูปจะข้ามขั้นนี้ไปเลย) ·
กด `c` เพื่อบังคับ calibrate สดใหม่ได้ทุกเมื่อ — ปุ่มนั้น**ทับค่าจากรูปด้วย**
และจะไม่กลับไปใช้ค่าจากรูปอีกจนกว่าคนนั้นจะได้ id ใหม่

## การปรับค่าให้เข้ากับตัวเอง

ทุกค่าอยู่ใน `.env` — ไม่ต้องแก้โค้ด

| อาการ | แก้ที่ |
|---|---|
| นับการหันบ่อยเกินไป | เพิ่ม `POSE_YAW_THRESHOLD` / `POSE_PITCH_THRESHOLD` |
| ขยับหัวเยอะแล้วไม่นับ | ลดค่าทั้งสองข้างบน |
| ค่ากระตุกไปมา | เพิ่ม `POSE_SMOOTH_FRAMES` และ `POSE_HOLD_SECONDS` |
| นับซ้ำรัว ๆ ตอนหันค้าง | ลด `POSE_RELEASE_RATIO` |
| กะพริบตาไม่ถูกนับ | ลด `BLINK_CLOSED_SCORE` (เช่น 0.4) |
| ขึ้นว่ากะพริบทั้งที่ลืมตาอยู่ | เพิ่ม `BLINK_CLOSED_SCORE` (เช่น 0.6) |
| ใช้วิธี EAR แล้วเกณฑ์ไม่เข้ากับคนบางคน | ปรับ `BLINK_EAR_CLOSE_RATIO` (ต่ำ = ต้องหลับตาสนิทกว่าถึงนับ) |
| ขึ้นว่าง่วงเร็วเกินไป | เพิ่ม `BLINK_DROWSY_SECONDS` |
| คนนั่งไกลขึ้น `too far` ทั้งที่อยากวิเคราะห์ | ลด `QUALITY_MIN_INTEROCULAR_PX` หรือเพิ่ม `CAMERA_WIDTH/HEIGHT` |
| id สลับกันตอนคนเดินไขว้ | เพิ่ม `TRACKER_WEIGHT_SIZE` · ตรวจว่า `TRACKER_SWAP_GUARD=true` |
| คนเดินเร็วแล้วได้ id ใหม่ตลอด | เพิ่ม `TRACKER_MAX_DISTANCE` · ตรวจว่า `TRACKER_USE_PREDICTION=true` |
| ระบบหน่วง / CPU สูง | ลด `MODEL_MAX_FACES` · ลด `CAMERA_FPS` · ปิด `DISPLAY_DRAW_MESH` |

**ถ้าใช้ `BLINK_METHOD=auto` (ค่าเริ่มต้น) ไม่ต้องหาค่า EAR เอง** — blendshape จัดการให้แล้ว
ตัวเลขที่แสดงบนหน้าจอคือ `eye` ซึ่งเป็นคะแนน 0–1 (สูง = ตาปิด) เทียบกับ `BLINK_CLOSED_SCORE`

**ถ้าจำเป็นต้องใช้ EAR** ระบบเรียน baseline ของแต่ละคนให้อัตโนมัติตอน calibrate —
แค่ให้ทุกคนมองตรงและลืมตาปกติ 3 วินาทีแรกก็พอ

## ใช้โทรศัพท์อยู่หรือเปล่า (`PHONE_ENABLED` — เปิดไว้)

โหมดติดตามกิจกรรมจะบอกด้วยว่าใครกำลังใช้โทรศัพท์ — ป้าย `PHONE` บนกรอบใบหน้า
และคอลัมน์ `phone` ในตาราง `focus`

ใช้ MediaPipe **Object Detector** (EfficientDet-Lite0, COCO 90 คลาส) โดยเปิด
`category_allowlist` ไว้ที่คลาสเดียวคือ `cell phone` — อีก 89 คลาสถูกตัดตั้งแต่ใน
ตัวโมเดล ไม่ได้เอามากรองทีหลัง

### ⚠️ "เจอโทรศัพท์" ไม่ใช่ "มีคนใช้โทรศัพท์"

นี่คือเหตุผลทั้งหมดที่มี `phone.py` แทนที่จะเรียกตัวตรวจแล้วรายงานตรง ๆ
โทรศัพท์ที่วางบนโต๊ะ วางชาร์จข้างผนัง หรืออยู่ในมือคนที่เดินผ่านหลังห้อง
ถูกตรวจเจอเหมือนกันหมด · ถ้ารายงานทุกกรอบที่เจอ ตัวเลข "เวลาที่ใช้โทรศัพท์"
จะกลายเป็น "เวลาที่มีโทรศัพท์อยู่ในห้อง" ซึ่งแทบไม่เปลี่ยนทั้งวัน

โปรแกรมจึงรายงานเฉพาะเครื่องที่**จับคู่กับคนได้** ด้วยหลักฐานสองชั้น:

| ชั้น | เงื่อนไข | ผลที่ได้ |
|---|---|---|
| **วัดได้** | อยู่ห่างจากข้อมือที่**มองเห็นจริง**ไม่เกิน `PHONE_HAND_REACH` เท่าของความกว้างไหล่ | `phone_confident = true` |
| **เดา** | มองไม่เห็นข้อมือ แต่โทรศัพท์อยู่ใน "ช่องใต้ใบหน้า" ของคนนั้น | `phone_confident = false` |

ชั้นเดามีไว้เพราะกล้องตั้งโต๊ะเห็นแค่หัวกับไหล่เป็นปกติ — ถ้าไม่มี ฟีเจอร์นี้จะไม่เคย
ทำงานเลยบนมุมกล้องที่ใช้จริง · แต่ต้องรู้ว่ามันคือการเดา จึงติดธงไว้แทนที่จะกลืนรวมกัน

**ช่องใต้ใบหน้าวัดสองแกนแยกกัน ไม่ใช่รัศมีอันเดียว** — ข้อนี้มาจากการวัดของจริง:
ทดสอบกับรูปใน `faces/` ตัวตรวจเห็นของสี่เหลี่ยมมืดบนโต๊ะที่มุมขวาล่างของภาพ
(คะแนน 0.40) ซึ่งอยู่ห่างจากใบหน้าคนในภาพเพียง ~1.3 เท่าของความกว้างใบหน้า
รัศมีเดียวที่กว้างพอจะครอบโทรศัพท์ที่ถืออยู่ระดับตัก ย่อมครอบของบนโต๊ะข้าง ๆ ไปด้วย
เสมอ · มือคนอยู่ใน**แนวดิ่งใต้หัว** จึงยอมให้ห่างลงล่างได้ไกล (`PHONE_FACE_BELOW`)
แต่ห่างออกข้างได้น้อย (`PHONE_FACE_SIDE`)

### เมื่อป้ายไม่ขึ้นทั้งที่คนกำลังเล่นอยู่

กรอบสีส้มบนจอคือ**ทุกเครื่องที่ตัวตรวจเห็น** รวมเครื่องที่จับคู่กับคนไม่ได้ —
วาดไว้เพื่อแยกสองสาเหตุนี้ออกจากกัน ซึ่งแก้คนละทาง:

| บนจอ | แปลว่า | แก้ที่ |
|---|---|---|
| ไม่มีกรอบส้มเลย | ตัวตรวจไม่เห็นโทรศัพท์ | ลด `PHONE_MIN_SCORE` · เปลี่ยนเป็น `efficientdet_lite2` |
| มีกรอบส้ม แต่ไม่มีป้าย `PHONE` | เห็นแล้วแต่จับคู่กับคนไม่ได้ | เพิ่ม `PHONE_HAND_REACH` / `PHONE_FACE_SIDE` |

### ราคาที่ต้องจ่าย

วัดบนเครื่องพัฒนา (Windows, CPU): **~54 ms ต่อการตรวจหนึ่งครั้ง**
ที่ `PHONE_EVERY_N_FRAMES=8` และกล้อง 20fps = ราว 2.5 ครั้ง/วินาที ≈ 13% ของหนึ่งคอร์
บน Pi 5 ให้เผื่อไว้ 2–3 เท่า

⚠️ ค่านี้ถูก**ปัดขึ้นให้เป็นจำนวนเท่าของ `BODY_EVERY_N_FRAMES` เสมอ** เพราะการจับคู่
ต้องใช้ตำแหน่งข้อมือของเฟรมเดียวกัน ไม่ใช่ของเมื่อสี่เฟรมก่อน · ตั้ง `PHONE_ENABLED=false`
เพื่อปิดทั้งหมดถ้า CPU ไม่พอ

## จำนวนคนกับภาระ CPU

ประมาณการบน Raspberry Pi 5 ที่ 640×480 · 15 fps (ยังไม่ได้วัดบนเครื่องจริง)

| `MODEL_MAX_FACES` | CPU โดยประมาณ | เหมาะกับ |
|---|---|---|
| 1–2 | ~25–35% ของหนึ่งคอร์ | โต๊ะทำงานส่วนตัว |
| **6** *(ค่าเริ่มต้น)* | ~45–60% | ห้องเรียนเล็ก · ห้องประชุม |
| 10+ | > 80% | ⚠️ เสี่ยงเบียดเวลา thread ของ SGP30 ที่ต้องอ่านทุก 1 วินาทีเป๊ะ |

> ⚠️ **อย่าตั้งเกิน 6 ถ้ารันพร้อมกับ collector ของเซนเซอร์** — SGP30 ต้องอ่านที่ 1 Hz พอดี
> ถ้า CPU ตึงจน thread นั้นพลาดจังหวะ ค่า TVOC จะ drift โดยไม่มี error ให้เห็น
> ควรรัน `htop` ดูจริงก่อนเพิ่ม

> ⚠️ **`CAMERA_MIRROR` กำหนดว่าป้าย `Left`/`Right` หมายถึงด้านไหน**
> ค่าเริ่มต้น `true` (ภาพเหมือนส่องกระจก) ทำให้ `Right` = ด้านขวาของตัวคุณเอง
> ถ้าเปลี่ยนเป็น `false` ระบบจะสลับป้ายให้อัตโนมัติ — แต่ควรดูผลบนจอยืนยันอีกที

## ต่อกับแดชบอร์ด

`WindowSummary.to_focus_row()` คืน dict ที่ตรงกับตาราง `focus` ใน Supabase อยู่แล้ว:

```python
{"person": 1, "movement": 6, "direction": {"Left": 2, "Right": 3, "Up": 0, "Down": 1},
 "face_count": 1, "name": "สมชาย", "emotion": "happy",
 "posture": "sitting", "posture_confident": True,
 "phone": False, "phone_confident": True}
```

⚠️ `name` · `emotion` · `posture` · `posture_confident` · `phone` · `phone_confident`
เป็นคอลัมน์ใหม่ ต้องเพิ่มในตาราง `focus` ก่อนถึงจะ INSERT ได้:

```sql
ALTER TABLE focus
  ADD COLUMN IF NOT EXISTS name              text,
  ADD COLUMN IF NOT EXISTS emotion           text,
  ADD COLUMN IF NOT EXISTS posture           text,
  ADD COLUMN IF NOT EXISTS posture_confident boolean,
  ADD COLUMN IF NOT EXISTS phone             boolean,
  ADD COLUMN IF NOT EXISTS phone_confident   boolean;
```

> ⚠️ **ต้องรันก่อนอัปเดต ไม่ใช่หลัง** — `to_focus_row()` ส่งคีย์ทุกตัวเสมอแม้ค่าจะเป็น
> `null` · PostgREST ตอบ 400 เมื่อเจอคอลัมน์ที่ไม่มีจริง และ `uploader.py` ถือว่า
> 4xx คือ "ส่งใหม่ก็ได้ผลเดิม" จึง**ทิ้งแถวนั้นแล้วเดินต่อ** (ดู `_deliver`)
> ผลคือข้อมูลกล้องหยุดไหลทั้งหมดโดยที่โปรแกรมยังดูเหมือนทำงานปกติ —
> มีแค่บรรทัด `[uploader] HTTP 400 — ทิ้งแถวนี้` ใน console เป็นสัญญาณเดียว

`posture` เป็น `standing` · `sitting` · `lying` (ค่าคงที่ใน `body.py`) มาจากท่าของ
คนที่ถูกรายงานในหน้าต่างนั้น ผ่าน `PostureHold` มาแล้วจึงไม่กระพริบตามเฟรม

⚠️ **`posture_confident=false` ไม่ใช่รายละเอียดที่ข้ามได้** `body.posture()` ตอบทุกครั้ง
แม้ตอนที่ขาถูกโต๊ะบัง ซึ่งกล้องตั้งโต๊ะเจอเป็นปกติ — คำตอบตอนนั้นคือการเดาจากหลักฐาน
อ้อม ("ขาหายไปทั้งที่ตัวอยู่กลางเฟรม แปลว่าน่าจะมีโต๊ะบัง") ไม่ใช่การวัดมุมต้นขาจริง
แดชบอร์ดจึงเติม `?` ต่อท้ายท่าที่ค่านี้เป็น false แทนที่จะแสดงเหมือนท่าที่วัดได้
`null` = หน้าต่างนั้นไม่มีท่าเลย (โหมดห้องรวม หรือโหมดที่ไม่ได้เปิดการดูร่างกาย)

`phone` = คนที่ถูกรายงานกำลังใช้โทรศัพท์อยู่ไหมตอนปิดหน้าต่าง · `phone_confident=false`
คือจับคู่ได้จากตำแหน่ง (โทรศัพท์อยู่ในช่องใต้ใบหน้าคนนี้) เพราะมองไม่เห็นข้อมือ
ความหมายเดียวกับ `posture_confident` ทุกประการ

⚠️ **`null` กับ `false` ไม่เหมือนกันและห้ามรวมกัน** — `null` = ไม่ได้ตรวจเลย
(ปิดไว้ · โหมดอื่น · โมเดลโหลดไม่ขึ้น) ส่วน `false` = ตรวจแล้วไม่มีใครใช้
ปลายทางที่นับสองอย่างนี้เป็นค่าเดียวจะรายงานว่า "ไม่มีใครเล่นโทรศัพท์" ในวันที่
ไม่มีใครดูเลย ซึ่งเป็นคำตอบที่ผิดในทางที่ดูน่าเชื่อที่สุด

`person` ยังเป็น**หมายเลข track** เหมือนเดิม ไม่ได้ถูกแทนด้วยชื่อ — เก็บทั้งสองอย่าง
เพราะเป็นตัวตนต่างชนิดกัน: หมายเลขคือ "คนเดิมในเซสชันนี้" ส่วนชื่อคือ "คนนี้คือใคร"
ซึ่งอาจไม่รู้ก็ได้ · `None` แปลว่า **ไม่รู้** ไม่ใช่ค่าว่าง

คอลัมน์เหล่านี้คือสิ่งที่ `hooks/useFocus.js` และ `components/FocusSection.jsx` อ่านอยู่
และหน้าต่าง 15 วินาทีก็ตรงกับที่แดชบอร์ดคาดหวัง (`FOCUS_BUCKET_MS` รวม 4 ช่วง = 1 นาที)

### ส่งข้อมูลจริง — `uploader.py`

ใส่ค่าสามตัวใน `pi-vision/.env` แล้วมันส่งเอง ไม่ต้องแก้โค้ด:

```
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_ANON_KEY=eyJ...
SUPABASE_FOCUS_TABLE=focus
```

**ไม่ใส่ = ไม่ส่ง** โปรแกรมยังทำงานและแสดงผลบนจอครบเหมือนเดิม

สิ่งที่ตัวส่งรับประกัน:

| สถานการณ์ | พฤติกรรม |
|---|---|
| ส่งช้า/ค้าง | ส่งจาก**เธรดแยก** · ลูปกล้องไม่เคยรอเครือข่าย |
| 5xx · timeout · เน็ตหลุด | ลองใหม่ หน่วงเพิ่มเป็นเท่าตัวถึงเพดาน 60s · แถวยังอยู่ในคิว |
| 4xx (payload ผิด · key ผิด) | **ไม่ลองใหม่** ทิ้งแถวพร้อมบอกเหตุผล — ลองอีกก็ผิดเหมือนเดิมและจะตันคิว |
| ออฟไลน์นาน | เขียนคิวลงดิสก์ (`queue.jsonl`) · รอบถัดไปอ่านกลับมาส่งต่อ |
| คิวเต็ม (5,000 แถว) | ทิ้ง**แถวเก่าสุด** ก่อน ข้อมูลใหม่มีค่ากว่า |
| ปิดโปรแกรม | พยายามส่ง 2 วินาที แล้วเก็บที่เหลือลงดิสก์ |

**เรื่องอายุการ์ด SD:** ไม่เขียนดิสก์ทุกแถวที่ส่งไม่ผ่าน เขียนเมื่อหน่วงถึงเพดาน
(แปลว่าออฟไลน์นานจริง) และตอนปิดโปรแกรมเท่านั้น — แลกกับความเสี่ยงว่าถ้าไฟดับ
ระหว่างที่ยังไม่ถึงเพดาน จะเสียแถวที่ค้างใน RAM

โหมดห้องรวมมี payload คนละแบบ (`to_room_row()` ไม่มีคอลัมน์ `person` เลย) ต้องมีตาราง
ของตัวเองผ่าน `SUPABASE_ROOM_TABLE` — เว้นว่าง = โหมดนั้นไม่ส่งข้อมูล

**เหลืออีกอย่างเดียว:** systemd unit ให้รันอัตโนมัติตอนบูต พร้อม `Restart=always`

## 🔒 ความเป็นส่วนตัว — อ่านก่อนใช้กับผู้อื่น

### สิ่งที่ยังเป็นจริงเหมือนเดิม

- ประมวลผลภาพบน Pi ทั้งหมด · **ไม่ส่งภาพออกไปไหน**
- **ไม่บันทึกภาพหรือวิดีโอลงดิสก์เลย**
- **ไม่มีการเก็บอะไรลงดิสก์** — ทุกอย่างอยู่ใน RAM และหายเมื่อปิดโปรแกรม
  (ยกเว้นรูปที่**คุณวางเอง**ใน `faces/` — ดูหัวข้อถัดไป)

### ⚠️ สิ่งที่เปลี่ยนไปเมื่อวางรูปใน `faces/`

สามข้อข้างบนเขียนไว้ตอนที่ระบบ**จำหน้าใครไม่ได้เลยโดยตั้งใจ** การวางรูปเปลี่ยนเรื่องนี้:

| ก่อน | หลังวางรูป |
|---|---|
| ข้อมูลผูกกับหมายเลขที่หายไปเมื่อปิดโปรแกรม | ข้อมูลผูกกับ **ชื่อคนจริง** ที่คงอยู่ข้ามการรีสตาร์ต |
| ไม่มีภาพใบหน้าบนดิสก์ | **มีภาพใบหน้าบนดิสก์** ในโฟลเดอร์ที่คุณวาง |
| ย้อนกลับเป็นตัวบุคคลไม่ได้ | ย้อนได้ทันที เพราะชื่ออยู่ในชื่อไฟล์ |

ก่อนใส่รูปของใคร **ควรได้รับความยินยอมจากเจ้าของใบหน้า** และไม่ควรวางโฟลเดอร์นี้
ในที่ที่แชร์กับคนอื่นหรือ sync ขึ้นคลาวด์ · ลบรูปออก = ระบบกลับไปใช้หมายเลขทันที
โดยไม่ต้องแก้ค่าตั้งอะไร

**อารมณ์**ก็เป็นข้อมูลอ่อนไหวเช่นกัน เมื่อผูกกับชื่อจะกลายเป็นบันทึกว่าใครอารมณ์ไหน
ตอนไหน — ปิดได้ด้วย `EMOTION_ENABLED=false` ถ้าไม่จำเป็นต่อสิ่งที่ต้องการวัด

### โหมดห้องรวมไม่มีประเด็นนี้เลย

หัวข้อข้างล่างทั้งหมด**ใช้กับโหมดรายบุคคลเท่านั้น** โหมดห้องรวมไม่เรียก `face_signature()`
และไม่เรียก `average_ear()` สักครั้งเดียว จึงไม่มีลายเซ็นให้เก็บตั้งแต่แรก
ไม่วัดดวงตาของใคร และไม่แสดง id บนหน้าจอด้วย
(`test_room_smoke.py` ดักทั้งการเรียกฟังก์ชันและทุกข้อความที่ถูกวาดลงภาพ
เพื่อยืนยันสามข้อนี้ทุกครั้งที่รันเทส)

**ถ้าไม่จำเป็นต้องรู้ว่าใครเป็นใคร ให้ใช้โหมดห้องรวม** — ตอบคำถามของโครงงานได้ครบ
โดยไม่ต้องแตะข้อมูลชีวมิติ และอธิบายกับกรรมการหรือผู้ถูกบันทึกได้ง่ายกว่ามาก

### ⚠️ สิ่งที่เปลี่ยนไปเมื่อเปิด re-identification (โหมดรายบุคคล)

การจำ id ได้เมื่อคนกลับเข้าเฟรม **แลกมาด้วยการเก็บ "ลายเซ็นโครงหน้า"** ซึ่งเป็น
**ข้อมูลชีวมิติแบบอ่อน (weak biometric)** — ต้องเข้าใจให้ตรงกันก่อนตัดสินใจ

| ประเด็น | ความจริง |
|---|---|
| เก็บอะไร | ตัวเลข 8 ตัว ที่เป็นสัดส่วนระหว่างระยะทางบนใบหน้า |
| ย้อนกลับเป็นภาพได้ไหม | **ไม่ได้** — ข้อมูลน้อยเกินกว่าจะสร้างภาพใบหน้าขึ้นมาใหม่ |
| ระบุตัวตนได้ไหม | **ระบุซ้ำภายในเซสชันได้** แต่เทียบกับฐานข้อมูลภายนอกไม่ได้ |
| เก็บนานแค่ไหน | ค่าเริ่มต้น 3600 วินาทีหลังคนหายจากเฟรม หรือจนกว่าจะเกิน 30 คน แล้วลืมถาวร |
| เก็บที่ไหน | **RAM เท่านั้น** ไม่เขียนลงดิสก์ ปิดโปรแกรมแล้วหายหมด |
| ปิดได้ไหม | ได้ 2 ทาง — ใช้โหมดห้องรวม (ไม่คำนวณเลย) หรือ `TRACKER_REID_ENABLED=false` |
| ลืมทันทีได้ไหม | ได้ — กด `f` ระหว่างรัน |

> ⚖️ **ในเชิง PDPA ลายเซ็นนี้ถือเป็นข้อมูลส่วนบุคคล** เพราะใช้แยกแยะบุคคลได้
> ถ้าติดตั้งในพื้นที่ที่มีคนอื่น **ต้องแจ้งและขอความยินยอมก่อน** และควรอธิบายให้ชัดว่า
> เก็บอะไร นานแค่ไหน และปิดได้อย่างไร
>
> เอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย — ถ้าเป็นโครงการที่ใช้กับผู้อื่นจริง ควรปรึกษาผู้รู้ก่อน

**ถ้าไม่จำเป็นต้องจำ id ข้ามการเข้า-ออก ให้ปิดไว้** — ระบบยังติดตามคนในเฟรมได้ปกติทุกอย่าง
เสียแค่ว่าคนที่เดินออกไปแล้วกลับมาจะได้หมายเลขใหม่

## ความแม่นยำของ re-identification ที่วัดได้จริง

ทดสอบด้วยใบหน้าสังเคราะห์ 3 แบบ + สัญญาณรบกวนที่ landmark
วัดระยะห่างของลายเซ็นระหว่าง "คนเดียวกัน" กับ "คนละคน"

| noise ที่ landmark | เฉลี่ยกี่เฟรม | คนเดียวกัน (สูงสุด) | คนละคน (ต่ำสุด) | แยกออกไหม |
|---|---|---|---|---|
| ±1% | **1** | 0.095 | 0.069 | ❌ **แยกไม่ออก** |
| ±1% | 10 | 0.030 | 0.069 | ✅ |
| ±2% | **1** | 0.159 | 0.081 | ❌ **แยกไม่ออก** |
| ±2% | 15 | ~0.045 | 0.077 | ✅ |
| ±3% | 10 | 0.115 | 0.072 | ❌ |
| ±3% | 30 | 0.063 | 0.066 | ⚠️ เฉียดฉิว |

**ข้อสรุปที่สำคัญที่สุด: ลายเซ็นจากเฟรมเดียวแยกคนไม่ออกเลย**
เพราะ landmark สั่นระหว่างเฟรมมากกว่าความต่างระหว่างคนที่หน้าคล้ายกัน

ระบบจึง**บังคับให้สะสมอย่างน้อย 15 เฟรม** (`TRACKER_REID_MIN_SAMPLES`) ก่อนยอมใช้จับคู่
คนที่เพิ่งเข้ามาจะได้ id ชั่วคราวก่อน แล้วค่อยเปลี่ยนเป็น id เดิมเมื่อมั่นใจ

### กันการจำสลับคนด้วยสามชั้น

| ชั้น | ทำอะไร |
|---|---|
| ขนาดใบหน้า | ใบหน้าเล็กกว่า `TRACKER_REID_MIN_SIZE` ไม่เอามาเรียนหรือเทียบเลย |
| threshold | ต้องห่างน้อยกว่า 0.05 (ต่างกันเฉลี่ย 5%) |
| **ratio test** | ตัวที่ใกล้ที่สุดต้องดีกว่าอันดับสองชัดเจน — ถ้าสองคนคล้ายกันพอ ๆ กัน **แปลว่าเดาไม่ได้ จึงไม่เดา** |

> 🔑 **หลักการออกแบบ: แจก id ใหม่ผิด เสียหายน้อยกว่ารวมข้อมูลสองคนเข้าด้วยกันมาก**
> ทุก threshold จึงตั้งไว้ฝั่งอนุรักษ์นิยม ยอมพลาดการจำ ดีกว่าจำผิดคน

> ⚠️ **ตัวเลขข้างบนมาจากใบหน้าสังเคราะห์ ไม่ใช่ใบหน้าจริง**
> ใบหน้าคนจริงมีความหลากหลายและ landmark สั่นต่างจากที่จำลอง
> **ต้องทดสอบกับคนจริงและปรับ `TRACKER_REID_THRESHOLD` เอง** — ดูตัวเลข `reid` บน HUD
> ว่าจำได้กี่ครั้ง และสังเกตว่ามีการจำสลับคนหรือไม่

### id ชั่วคราว (provisional)

ระหว่างที่ยังสะสมลายเซ็นไม่พอ ระบบ**ยังตัดสินไม่ได้**ว่าคนที่เพิ่งเข้ามาเป็นคนใหม่
หรือคนเดิมที่เคยหายไป จึงให้ id ชั่วคราวไว้ก่อนและทำเครื่องหมาย `provisional`

| จุด | พฤติกรรมของ id ชั่วคราว |
|---|---|
| HUD | ขึ้นเป็น `#5?` — เครื่องหมาย `?` แปลว่ายังไม่ยืนยัน |
| ตาราง `focus` | **ไม่ถูกบันทึก** — ไม่งั้นข้อมูลของคนเดียวกันจะกระจัดกระจายอยู่หลาย id |
| เมื่อ re-ID สำเร็จ | เปลี่ยนกลับเป็น id เดิมและตัด `?` ทิ้ง |
| เมื่อลองครบ `TRACKER_REID_MAX_ATTEMPTS` แล้วยังไม่เข้ากับใคร | ยอมรับว่าเป็นคนใหม่จริง ตัด `?` ทิ้ง |

### ผลการวัด — 3 คน เดินเข้าออกสลับกัน

`python3 bench_reid.py` จำลอง 3 คนหลุดสั้น ๆ · เดินออกไปนาน · กลับเข้ามาพร้อมกัน

| ค่าตั้ง | id ที่ปลายทางเห็น | จำสลับคน |
|---|---|---|
| ปิด re-ID | 6 | 0 |
| เปิด re-ID แต่ไม่กรอง id ชั่วคราว | 6 | 0 |
| **ปัจจุบัน** | **3** ← เท่าจำนวนคนจริง | **0** |

จุดสำคัญ: การเปิด re-ID เฉย ๆ ไม่ช่วยลดจำนวน id ที่ปลายทางเห็น เพราะ id ชั่วคราว
ถูกบันทึกไปแล้วก่อนที่ระบบจะตัดสินใจได้ — **ต้องกรอง `provisional` ออกด้วยถึงจะได้ผล**

## ข้อจำกัดที่ควรรู้

| ข้อจำกัด | รายละเอียด |
|---|---|
| **head pose เป็นค่าประมาณ** | คำนวณจากเรขาคณิตของ landmark ไม่ใช่การแก้ปัญหา PnP จริง ใช้เทียบกับตัวเองได้ แต่ไม่ใช่องศาที่แม่นยำ |
| **re-ID เป็นการจำแบบอ่อน** | ลายเซ็นโครงหน้า 8 มิติแยกคนที่หน้าคล้ายกันมากไม่ได้ · ทดสอบกับใบหน้าสังเคราะห์เท่านั้น ยังไม่ได้ยืนยันกับคนจริง |
| **ต้องเห็นหน้าชัดอย่างน้อย 15 เฟรม** | คนที่เดินผ่านเร็ว ๆ หรืออยู่ไกล จะไม่ถูกจำ — ได้ id ใหม่ทุกครั้ง |
| **ต้องมีแสงพอ** | ต่ำกว่า ~100 lx MediaPipe เริ่มตรวจไม่เจอ — ใช้ค่าจาก BH1750 เตือนผู้ใช้ให้เปิดไฟได้ |
| **แว่นตาสะท้อนแสง** | ทำให้ EAR คลาดเคลื่อน ควร calibrate threshold ใหม่ |
| **กิน CPU** | ~25–35% ของหนึ่งคอร์ที่ 640×480 15fps — อย่าเร่งเป็น 1080p 30fps ไม่งั้นจะไปแย่งเวลา thread ของ SGP30 ที่ต้องอ่านทุก 1 วินาทีเป๊ะ |

## 1. ภาพรวม

Raspberry Pi 5 ทำหน้าที่แทน Arduino UNO Q ทั้งหมด — อ่านเซนเซอร์ทุกตัวเอง แล้วส่ง JSON เข้า
`POST /api/ingest` ของเว็บ Next.js ตามเดิม **API contract ฝั่งเว็บไม่เปลี่ยนรูปแบบ** เพียงเพิ่ม field ใหม่

```
┌──────────────────────── Raspberry Pi 5 (device_id: pi5-room1) ────────────────────────┐
│                                                                                        │
│   I2C-1 (GPIO2/3, 3.3V, 100 kHz)          UART0 (GPIO14/15, 9600 8N1)                 │
│   ├── SCD40      0x62  CO₂ / T / RH       └── PMS7003   PM1.0 / PM2.5 / PM10          │
│   ├── SGP30      0x58  TVOC / eCO₂                                                     │
│   ├── BH1750     0x23  lux                 USB 2.0                                     │
│   └── ADS1115    0x48  ← MQ-2 (analog)     ├── USB microphone → dBA                    │
│                                            └── (ทางเลือก) USB webcam                   │
│                                                                                        │
│   CSI-2 (22-pin)                                                                       │
│   └── Camera Module 3 → face / EAR / motion                                            │
│                                                                                        │
│   ┌────────────────── collector service (Python, systemd) ──────────────────┐          │
│   │  แต่ละเซนเซอร์ = 1 module + 1 thread ตามรอบของตัวเอง → shared snapshot   │          │
│   │  uploader อ่าน snapshot ทุก UPLOAD_INTERVAL_S แล้ว POST                  │          │
│   └──────────────────────────────────────────────────────────────────────────┘          │
└────────────────────────────────────────┬───────────────────────────────────────────────┘
                                         │ HTTPS  POST /api/ingest
                                         ▼
                          Next.js (Vercel) ──► Supabase `environment`
                                         │
                                         └──► Dashboard + Gemini analysis
```

## 2. ตารางสรุปเซนเซอร์ทั้งหมด

| # | อุปกรณ์ | วัดค่า | หน่วย | ช่วงวัด | อินเทอร์เฟซ | ที่อยู่ / พอร์ต | ไฟเลี้ยง | เอกสาร |
|---|---|---|---|---|---|---|---|---|
| 1 | **PMS7003** | PM1.0, PM2.5, PM10 | µg/m³ | 0–500 (สูงสุด ≥1000) | UART 9600 8N1 | `/dev/ttyAMA0` | 5V (ลอจิก 3.3V) | [→](devices/pms7003.md) |
| 2 | **SCD40** | CO₂ | ppm | 0–40,000 | I2C | `0x62` | 3.3V | [→](devices/scd40.md) |
| 2 | **SCD40** | อุณหภูมิ | °C | −10 ถึง 60 | I2C | `0x62` | 3.3V | [→](devices/scd40.md) |
| 2 | **SCD40** | ความชื้นสัมพัทธ์ | %RH | 0–100 | I2C | `0x62` | 3.3V | [→](devices/scd40.md) |
| 3 | **SGP30** | TVOC | ppb | 0–60,000 | I2C | `0x58` | 3.3V (ผ่าน breakout) | [→](devices/sgp30.md) |
| 3 | **SGP30** | eCO₂ | ppm | 400–60,000 | I2C | `0x58` | 3.3V (ผ่าน breakout) | [→](devices/sgp30.md) |
| 4 | **BH1750** | ความสว่าง | lux | 1–65,535 | I2C | `0x23` | 3.3V | [→](devices/bh1750.md) |

| 6 | **MQ-2** *(legacy)* | ก๊าซติดไฟรวม | ppm (ประมาณ) | 300–10,000 | analog → ADS1115 | `0x48` ch0 | ฮีตเตอร์ 5V | [→](devices/mq2-ads1115.md) |
| 7 | **กล้อง** | face / EAR / motion | — | — | CSI-2 หรือ USB | — | จากบอร์ด/USB | [→](devices/camera.md) |

### ความแม่นยำที่คาดหวัง

| ค่า | ความแม่นยำตาม datasheet | หมายเหตุ |
|---|---|---|
| PM2.5 | ±10 µg/m³ @ 0–100 · ±10% @ 100–500 | ค่า consistency error ระหว่างตัวเซนเซอร์ |
| CO₂ (SCD40) | ±(50 ppm + 5% ของค่าที่อ่าน) @ 400–2,000 ppm | ต้องตั้ง temperature offset ให้ถูก |
| อุณหภูมิ (SCD40) | ±0.8 °C @ 15–35 °C | ต้องตั้ง temperature offset ให้ถูก |
| ความชื้น (SCD40) | ±6 %RH @ 15–35 °C, 20–65 %RH | ต้องตั้ง temperature offset ให้ถูก |
| TVOC / eCO₂ | เป็นสัญญาณเชิงเปรียบเทียบ ไม่ใช่ค่าสัมบูรณ์ | eCO₂ **ไม่ใช่ CO₂ จริง** — ใช้ SCD40 เป็นค่าอ้างอิง |
| lux | ±20% ทั่วไป (ก่อนชดเชยกระจก/ฝาครอบ) | |

> ⚠️ **SGP30 `eCO₂` กับ SCD40 `co2` เป็นคนละสิ่ง** — eCO₂ คือค่าประมาณจากสัญญาณ VOC ไม่ได้วัด CO₂ โดยตรง
> บนแดชบอร์ดควรแสดง `co2` (SCD40) เป็นค่าหลัก และใช้ `eco2` เป็นตัวช่วยตรวจจับ VOC เท่านั้น

## 3. รอบการอ่านค่า (sampling schedule)

แต่ละเซนเซอร์มีรอบของตัวเองซึ่งกำหนดโดย datasheet — **ห้ามยัดทุกตัวไว้ใน loop เดียวกัน**
โครงสร้างที่แนะนำคือ 1 thread ต่อ 1 เซนเซอร์ เขียนลง shared snapshot dict ที่มี lock
แล้วให้ uploader อ่าน snapshot ไปส่งตามรอบของมันเอง

| เซนเซอร์ | รอบที่ต้องใช้ | บังคับแค่ไหน | เหตุผล |
|---|---|---|---|
| **SGP30** | **1.000 วินาที** | 🔴 บังคับเป๊ะ | อัลกอริทึม dynamic baseline ปรับจูนมาสำหรับ 1 Hz เท่านั้น ถ้าคลาดเคลื่อนค่าจะ drift |
| **SCD40** | 5 วินาที | 🟠 กำหนดโดยเซนเซอร์ | `start_periodic_measurement` อัปเดตค่าทุก 5 วินาที อ่านถี่กว่านั้นได้ค่าเดิม |
| **PMS7003** | ~2.3 วินาที (โหมด stable) | 🟢 เซนเซอร์ push เอง | อ่านจาก UART buffer แบบ event-driven เร่งความถี่เองไม่ได้ |
| **BH1750** | 120 ms (โหมดความละเอียดสูง) | 🟢 ยืดหยุ่น | อ่านทุก 1 วินาทีก็พอสำหรับแดชบอร์ด |
| **ไมโครโฟน** | หน้าต่าง RMS 1 วินาที | 🟢 ยืดหยุ่น | อ่าน stream ต่อเนื่อง สรุปเป็น dBA ต่อวินาที |
| **MQ-2** | 1 วินาที | 🟢 ยืดหยุ่น | เฉลี่ยหลายตัวอย่างเพื่อลด noise |
| **อัปโหลด → `/api/ingest`** | **5 วินาที** | 🟢 ปรับได้ | ตรงกับ `CLIENT_POLL_MS_DEFAULT = 5000` ใน `config/index.js` |

### ทำไมต้องอัปโหลดทุก 5 วินาที

`config/index.js → client.pollMsDefault` ตั้งไว้ที่ 5000 ms และ `pollMsMin` = 3000 ms
ถ้าอัปโหลดช้ากว่า 5 วินาที แดชบอร์ดจะ poll เจอแถวเดิมซ้ำ ๆ และ `DATA_AGE.freshMin` (3 นาที) ใน
`config/client.js` จะเริ่มขึ้นสีเหลืองเมื่อข้อมูลค้าง

> **กฎ:** ค่ารอบทุกตัวข้างบนต้องอยู่ในไฟล์ config ของ firmware ไม่ใช่เขียนตรง ๆ ในโค้ด
> เช่น `SGP30_INTERVAL_S`, `SCD40_INTERVAL_S`, `UPLOAD_INTERVAL_S` อ่านจาก `.env` พร้อมค่า default

## 4. โครงสร้างซอฟต์แวร์ที่แนะนำบน Pi 5

```
pi-collector/
├── .env                      # ค่าจริง (ไม่ commit)
├── .env.example              # เอกสารค่าทุกตัว
├── config.py                 # โหลด .env → dict เดียว ไม่มี literal กระจัดกระจาย
├── main.py                   # เริ่ม thread ทุกตัว + graceful shutdown
├── sensors/
│   ├── base.py               # BaseSensor: interval, read(), snapshot key, error backoff
│   ├── pms7003.py
│   ├── scd40.py
│   ├── sgp30.py
│   ├── bh1750.py
│   ├── microphone.py
│   └── mq2.py                # ผ่าน ADS1115
├── state.py                  # shared snapshot + threading.Lock
├── uploader.py               # POST /api/ingest + retry/backoff + offline queue
└── calibration/
    ├── baseline.json         # baseline ของ SGP30 (เขียนทุกชั่วโมง)
    └── mq2_r0.json           # ค่า R0 ของ MQ-2 หลัง calibrate
```

**หลักการที่ต้องยึด** (ตาม `cid-coding-style`):

- เพิ่มเซนเซอร์ตัวใหม่ = สร้างไฟล์ใหม่ใน `sensors/` + ลงทะเบียนใน config **ไม่แก้ `main.py`**
- ไม่มีตัวเลข/สตริง/URL เขียนตรง ๆ ในโค้ด — ที่อยู่ I2C, baud rate, รอบเวลา, endpoint ต้องมาจาก config
- เซนเซอร์ตัวใดตัวหนึ่งพังต้องไม่ทำให้ตัวอื่นหยุด — จับ exception ต่อ thread แล้ว backoff แบบ exponential
- ค่าที่อ่านไม่ได้ให้ส่งเป็น `null` (ไม่ใช่ `0`) เพราะ `analyzeReading()` ฝั่งเซิร์ฟเวอร์แยก "ไม่มีข้อมูล" กับ "ค่าเป็นศูนย์" ได้

## 5. ลำดับการบูตและ warm-up

ค่าที่อ่านได้ในช่วงแรกหลังเปิดเครื่อง **เชื่อถือไม่ได้** ต้องกันไว้ไม่ให้ขึ้นแดชบอร์ด

| เซนเซอร์ | เวลา warm-up | สิ่งที่เกิดขึ้นระหว่างนั้น |
|---|---|---|
| PMS7003 | **30 วินาที** | พัดลมต้องหมุนจนนิ่งก่อน ค่าก่อนหน้านั้นต่ำผิดปกติ |
| SGP30 | **15 วินาที** | คืนค่าคงที่ 400 ppm / 0 ppb เท่านั้น — ต้องทิ้ง |
| SGP30 (ครั้งแรกที่ติดตั้ง) | **12 ชั่วโมง** | ต้องรันต่อเนื่องเพื่อสร้าง baseline ที่ใช้ได้จริง |
| SCD40 | ~5 วินาที (1 รอบวัด) | ค่าแรกอาจคลาด ถ้ายังไม่ได้ตั้ง temperature offset |
| MQ-2 | **24–48 ชั่วโมง** (burn-in ครั้งแรก) · 3 นาที (ทุกครั้งที่บูต) | ฮีตเตอร์ต้องถึงอุณหภูมิทำงาน |
| BH1750 | ~1 วินาที | — |
| ไมโครโฟน | ทันที | — |

รายละเอียดขั้นตอน calibrate ทั้งหมดอยู่ที่ [04-calibration.md](04-calibration.md)

## 6. ข้อจำกัดที่รู้ล่วงหน้า

| ประเด็น | ผลกระทบ | ทางแก้ |
|---|---|---|
| Pi 5 ร้อนกว่า UNO Q มาก (SoC 5–12 W) | SCD40 อ่านอุณหภูมิสูงเกินจริงถ้าวางใกล้บอร์ด | ตั้ง `set_temperature_offset` + วางเซนเซอร์ห่างบอร์ด ≥10 cm ผ่านสาย I2C |
| พัดลม PMS7003 สร้างเสียงและกระแสลม | รบกวนไมโครโฟนและอาจดันฝุ่นเข้าเซนเซอร์อื่น | วางไมค์ห่างพัดลม + ปรับ dB offset ตอน calibrate |
| Pi 5 ไม่มี ADC | MQ-2 ต่อตรงไม่ได้ | ADS1115 + voltage divider ([→](devices/mq2-ads1115.md)) |
| SD card เสื่อมจากการเขียนบ่อย | ระบบพังหลังใช้งานยาว | เขียน baseline ทุก 1 ชั่วโมง ไม่ใช่ทุกวินาที · พิจารณาบูตจาก SSD ผ่าน PCIe |
| เน็ตหลุด | ข้อมูลหาย | uploader ต้องมี queue บนดิสก์ (จำกัดจำนวนแถว) แล้วส่งย้อนหลังเมื่อกลับมา |
